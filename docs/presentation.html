문제 & 목표 02 / 11

왜 이 시스템이 필요한가?

카카오 선물하기의 방대한 상품 중, 맥락에 맞는 선물을 추천하는 문제를 풉니다.

😓
문제 1 — 선택지 과부하
상품이 너무 많아 무엇을 골라야 할지 막막합니다. 관계나 상황을 고려한 탐색 경로가 없습니다.
🎯
문제 2 — 획일화된 추천
기존 베스트 상품 나열로는 개인의 취향, 피하고 싶은 품목, 예산 범위를 반영하기 어렵습니다.
✅
목표 1 — 맥락 인지 필터링
관계(친구/부모/연인), 상황(생일/명절), 예산, 피할 조건을 1차 필터로 적용해 후보를 좁힙니다.
⚡
목표 2 — 실시간 행동 반영
최근 클릭·노출·카트 이벤트를 즉시 feature store에 적재해 다음 추천에 바로 반영합니다.

추천 요청 흐름 04 / 11

Request Path — 4단계

사용자 조건 입력부터 카드 렌더까지의 데이터 흐름

1
브라우저 → rec-api POST /v1/recommendations
관계 · 상황 · 예산 · 성향(traits) · 피할 조건 · clickHistory를 JSON body로 전송합니다.
2
rec-api — 1차 필터 → 후보 생성 top-36
예산·피할 조건·오디언스로 1차 필터링 후, 관련도(관계·상황·성향 매치) + 인기도 점수 + 카테고리 다양성으로 top-36 추출. core-api로 candidateItems 전달.
3
core-api — Redis 최근 행동 병합 → LLM 랭킹 gpt-4o-mini
Redis에서 해당 유저/세션의 impressions · clicks · carts를 즉시 조회해 최근 행동을 병합. LLM이 후보 36개 안에서만 정렬 · 이유 · 배지를 JSON으로 생성합니다.
4
결과 → rec-api → 브라우저 카드 렌더 id · rank · score · reason · badges
LLM이 생성한 메타데이터와 함께 상품 카드가 렌더됩니다. 카드 클릭/노출 이벤트는 다시 /v1/events로 emit되어 실시간 feature store를 갱신합니다.
rec-api · 후보 생성 05 / 11

rec-api — Retrieval 단계

좋은 후보를 뽑는 것이 추천 품질의 절반입니다. 필터 → 스코어링 → 다양성의 3단 파이프라인.

🔍
① Hard Filter
예산 범위: minPrice ≤ 상품가 ≤ maxPrice
피할 조건: 사용자가 선택한 카테고리(뷰티·주방 등) 완전 제외
오디언스: 관계 태그와 맞지 않는 상품 필터
📊
② 관련도 스코어링
관계 매치 · 상황 매치 · 성향(traits) 매치 가중합
인기도(popularityScore) 보정 추가
→ 종합 점수로 내림차순 정렬
🌈
③ 카테고리 다양성
상위 점수 그룹 내에서 같은 카테고리가 뭉치지 않도록
round-robin 다양성 보정 → top-36 추출
데이터 소스
# data/gifts.json
상품 수: 200개
필드: id, name, price,
    category, tags,
    recommendationMeta

# recommendationMeta
audiences: ["friend",…]
occasions: ["birthday",…]
traits: 6종 성향 태그
popularityScore: 0–100
핵심 설계 의도
LLM에 200개를 전부 보내면 토큰 비용 폭발 + 품질 하락.
rec-api가 "맥락에 맞는 36개"를 미리 추려서 LLM이
후보 집합 안에서만 랭킹 · 설명하도록 역할을 분리합니다.
core-api · LLM 랭킹 06 / 11

core-api — Ranking 단계

후보 36개를 LLM이 최종 정렬하고, 이유와 배지를 생성합니다.

1
Redis 최근 행동 조회
impressions · clicks · carts 리스트를 user/session 키로 즉시 조회. 최근 본 카테고리를 컨텍스트에 주입.
2
LLM 프롬프트 구성
관계/상황/성향 + 최근 행동 + 후보 36개 메타를 JSON으로 조합해 gpt-4o-mini에 전달.
3
구조화 출력 JSON mode
LLM이 {id, rank, score, reason, badges} 배열로 응답. 후보 집합 안 id만 허용.
⚡
폴백 체계
키 없음 / API 오류 → 로컬 룰 기반 랭커
core-api 다운 → rec-api가 인기도 점수만으로 직접 반환
시스템 전체가 절대 죽지 않습니다.
🔄
LLM 전환 이력
초기 Anthropic Claude 기반으로 설계 → OpenAI gpt-4o-mini로 전환. 계약 기반(contract-first) JSON 인터페이스 덕분에 엔진 교체가 내부 변경에만 국한됩니다.
🏷️
badges 생성
LLM이 상황별 뱃지(예: "생일 추천", "트렌디", "가성비")를 자동 생성해 카드 UI에 표시. 추천 이유도 한국어로 생성합니다.

핵심 가치 — 실시간 반영

최근 본 카테고리가 다음 추천에 즉시 반영됩니다.

콜드스타트 & 회복탄력성 08 / 11

항상 동작하는 시스템

신규 유저도, 장애 상황도 graceful하게 처리합니다.

🆕
콜드스타트 — 신규 유저
Redis에 행동 이력이 없는 신규 유저.

→ 인기도(popularityScore) + 관련도 스코어만으로 top-36 구성
→ LLM이 맥락(관계/상황/성향)만으로 랭킹 + 이유 생성

행동 없어도 양질의 추천이 가능합니다.
🔧
core-api 장애
core-api 타임아웃 또는 연결 불가 상황.

→ rec-api가 인기도 점수 기반으로 직접 결과 반환
→ 추천 품질은 낮아지지만 서비스 중단 없음

fallback 상태를 응답에 명시.
🔑
OpenAI 키 없음 / LLM 오류
API 키 미설정 또는 rate limit / 응답 파싱 실패.

→ core-api 내 로컬 룰 기반 랭커로 즉시 폴백
→ 관련도 + 인기도 가중합 정렬 결과 반환

LLM 없이도 결과를 냅니다.
🛡️
설계 원칙 — Defence in Depth
3중 폴백 레이어:
LLM 실패 → 로컬 룰 랭커
core-api 실패 → rec-api 인기도 직접 반환
이벤트 파이프라인 장애 → 추천 요청 경로와 분리되어 있어 무관

정리 & 향후 방향 11 / 11

핵심 설계 요약 & 다음 단계

Retrieval–Ranking 분리 + 실시간 Feature Store + 계약 기반 인터페이스의 결합.

후보 생성 / 랭킹 분리
rec-api(retrieval) + core-api LLM(ranking). 토큰 비용 통제와 추천 품질을 동시에 달성.
실시간 Feature Store
Kafka → event-worker → Redis 파이프라인으로 클릭 1번이 다음 추천을 즉시 바꿉니다.
계약 기반 설계
docs/api-contract.md로 rec-api↔core-api JSON 계약 고정. 향후 gRPC 전환도 메시지 구조 변경 없이 가능.
3중 폴백 / 회복탄력성
LLM 오류 → 로컬 룰, core-api 다운 → 인기도 직접 반환. 절대 서비스 중단 없음.
향후 — Recency를 후보 생성에 반영
현재: 최근 행동은 core-api 랭킹 컨텍스트에만 사용. 다음: rec-api retrieval 단계에서 최근 본 카테고리를 후보 생성 가중치에 직접 반영해 니치 recency 강화.
향후 — 벡터 검색 / 임베딩
현재 키워드 매칭 기반 retrieval을 상품 설명 임베딩 + ANN 검색으로 교체해 의미 기반 후보 생성 품질 향상.
