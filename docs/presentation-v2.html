문제 & 목표 03 / 13

왜 이 시스템이 필요한가?

카카오 선물하기의 방대한 상품 중, 맥락에 맞는 선물을 추천하는 문제를 풉니다.

😓
문제 1 — 선택지 과부하
상품이 너무 많아 무엇을 골라야 할지 막막합니다. 관계나 상황을 고려한 탐색 경로가 없습니다.
🎯
문제 2 — 획일화된 추천
기존 베스트 상품 나열로는 개인의 취향, 피하고 싶은 품목, 예산 범위를 반영하기 어렵습니다.
✅
목표 1 — 맥락 인지 필터링
관계(친구/부모/연인), 상황(생일/명절), 예산, 피할 조건을 1차 필터로 적용해 후보를 좁힙니다.
⚡
목표 2 — 실시간 행동 반영
최근 클릭·노출·카트 이벤트를 즉시 feature store에 적재해 다음 추천에 바로 반영합니다.

추천 요청 흐름 05 / 13

Request Path — 4단계

사용자 조건 입력부터 카드 렌더까지의 데이터 흐름

1
브라우저 → rec-api POST /v1/recommendations
관계 · 상황 · 예산 · 성향(traits) · 피할 조건 · clickHistory를 JSON body로 전송합니다.
2
rec-api — 1차 필터 → 후보 생성 top-36 recency-aware
예산·피할 조건·오디언스로 1차 필터링 후, 관련도·인기도·recency 슬롯(R≈K/6)으로 top-36 추출. 최근 클릭 카테고리가 인기도에 밀려 사라지지 않도록 슬롯 예약. core-api로 candidateItems 전달.
3
core-api — Redis 최근 행동 병합 → LLM 랭킹 gpt-4o-mini 캐시 TTL 300s
Redis에서 impressions·clicks·carts 즉시 조회해 최근 행동 병합. model + 후보 id 집합 + preference 시그니처로 Redis 캐시 먼저 확인 — 히트 시 LLM 재호출 없이 즉답. 미스 시 LLM이 후보 36개 안에서 정렬·이유·배지를 JSON으로 생성.
4
결과 → rec-api → 브라우저 카드 렌더 id · rank · score · reason · badges · cached
LLM 메타데이터와 함께 카드 렌더. 캐시 사용 여부가 model.cached 플래그로 표시됩니다. 카드 클릭/노출 이벤트는 /v1/events로 emit되어 feature store를 갱신합니다.
rec-api · 후보 생성 06 / 13

rec-api — Retrieval 단계 (Recency-Aware)

좋은 후보를 뽑는 것이 추천 품질의 절반입니다. 필터 → 스코어링 → 다양성 → recency 슬롯의 4단 파이프라인.

🔍
① Hard Filter
예산 범위: minPrice ≤ 상품가 ≤ maxPrice
피할 조건: 사용자가 선택한 카테고리(뷰티·주방 등) 완전 제외
오디언스: 관계 태그와 맞지 않는 상품 필터
📊
② 관련도 스코어링
관계 매치 · 상황 매치 · 성향(traits) 매치 가중합
인기도(popularityScore) 보정 추가
→ 종합 점수로 내림차순 정렬
🌈
③ 카테고리 다양성
상위 점수 그룹 내에서 같은 카테고리가 뭉치지 않도록
round-robin 다양성 보정
🎯
④ Recency 슬롯 예약 Phase 1 신규
요청 clickHistory의 최근 카테고리/태그 분석.
전체 top-K(36) 중 R ≈ K/6 슬롯을 최근 클릭 카테고리 항목에 우선 예약.

인기도 점수가 낮아도 최근 관심 카테고리는 반드시 후보에 진입.
✓ 무이력: 가전 0/7 → 최근 가전 클릭 시: 가전 4/7 진입
신규 유저(이력 없음)는 기존과 동일하게 동작.
데이터 소스
# data/gifts.json
상품 수: 200개
필드: id, name, price,
    category, tags,
    recommendationMeta

# recommendationMeta
audiences: ["friend",…]
occasions: ["birthday",…]
traits: 6종 성향 태그
popularityScore: 0–100
core-api · LLM 랭킹 07 / 13

core-api — Ranking 단계 + LLM 캐시

후보 36개를 LLM이 최종 정렬하고, 반복 요청은 Redis 캐시로 즉답합니다.

1
Redis 최근 행동 조회
impressions · clicks · carts 리스트를 user/session 키로 즉시 조회. 최근 본 카테고리를 컨텍스트에 주입.
2
LLM 캐시 확인 Phase 2 신규
model + 후보 id 집합 + preference + limit + clickHistory 시그니처로 Redis 캐시 조회. 히트 시 즉시 반환 — LLM 재호출 없음. Redis 장애 시 그냥 통과.
3
LLM 프롬프트 구성 (캐시 미스 시)
관계/상황/성향 + 최근 행동 + 후보 36개 메타를 JSON으로 조합해 gpt-4o-mini에 전달.
4
구조화 출력 JSON mode
LLM이 {id, rank, score, reason, badges} 배열로 응답. 결과를 Redis에 TTL 300s로 저장. model.cached: false 플래그 반환.
⚡
폴백 체계
키 없음 / API 오류 → 로컬 룰 기반 랭커
core-api 다운 → rec-api가 1회 재시도 후 인기도 점수만으로 직접 반환
Redis 장애 → 캐시 미스로 간주, LLM 직접 호출
시스템 전체가 절대 죽지 않습니다.
🔄
LLM 전환 이력
초기 Anthropic Claude 기반으로 설계 → OpenAI gpt-4o-mini로 전환. 계약 기반(contract-first) JSON 인터페이스 덕분에 엔진 교체가 내부 변경에만 국한됩니다.
🏷️
badges 생성
LLM이 상황별 뱃지(예: "생일 추천", "트렌디", "가성비")를 자동 생성해 카드 UI에 표시. 추천 이유도 한국어로 생성합니다.

콜드스타트 & 회복탄력성 09 / 13

항상 동작하는 시스템

신규 유저도, 장애 상황도 graceful하게 처리합니다. v2에서 부팅 순서·재시도·헬스체크를 강화했습니다.

🆕
콜드스타트 — 신규 유저
Redis에 행동 이력이 없는 신규 유저.

→ 인기도(popularityScore) + 관련도 스코어만으로 top-36 구성
→ recency 슬롯 비활성 (이력 없으면 기존과 동일)
→ LLM이 맥락(관계/상황/성향)만으로 랭킹 + 이유 생성

행동 없어도 양질의 추천이 가능합니다.
🔧
core-api 장애 Phase 2 강화
core-api 타임아웃 또는 연결 불가 상황.

→ rec-api가 1회 자동 재시도 후 인기도 점수 기반으로 직접 결과 반환
→ fallback 상태를 응답에 명시
→ /healthz가 coreApiOk: false로 보고
🩺
Healthcheck & 부팅 순서 Phase 2 신규
docker compose healthcheck 구성:
core/rec-api: python urlopen
Redis: redis-cli ping

depends_on: service_healthy로 의존 서비스가 준비된 후에만 기동. 부팅 순서 보장.
🛡️
설계 원칙 — Defence in Depth
3중 폴백 레이어:
LLM 실패 → 로컬 룰 랭커
core-api 실패 → rec-api 인기도 직접 반환 (1회 재시도 후)
이벤트 파이프라인 장애 → 추천 요청 경로와 분리되어 있어 무관

requestId 구조적 로깅으로 장애 추적 가능.
